## 2026-09-08 — 프로젝트 시작

**배경.** Z-Weave를 Claude Code로 작업할 때 web 프로젝트 대비 UI 작업이 불편하다는 문제에서 출발했다. web에서는 Claude in Chrome으로 브라우저를 몰아 UI 버그를 재현·수정할 수 있는데, 데스크톱 앱은 사람이 화면을 캡처해 업로드해야 했다. 근본 원인은 Chrome에 CDP가 내장돼 있고 Z-Weave에는 없다는 것이다.

**설계 과정에서 방향이 세 번 바뀌었다.**

1. 처음에는 gtest 루프(코어 로직 버그)를 UI 캡처 루프보다 우선하려 했다. 드레이프·시뮬레이션 실패는 단위 테스트로 정상 기준을 정의할 수 없고(도메인 판단) 화면으로는 즉시 알 수 있다는 점 때문에 UI 쪽으로 우선순위를 되돌렸다.
2. 중간 계층을 앱 본체(`zwAppZWeave.cpp`)에 심는 방안 → Z-Weave 테스팅 빌드 하위 타겟 방안 → **완전 분리된 Qt 스타일 플러그인**으로 옮겼다. 사용자가 "별도 프로그램을 만들어서 각각 따로 실행"하는 구조를 요구했다. 기각 근거는 설계문서 §6에 남겼다.
3. 앱 내부 접근 없이는 메쉬 수치 판정이 불가능하다고 판단했다가 철회했다. `zwObjExporter`가 있으므로 OBJ로 익스포트해 **밖에서 파싱**하면 된다.

**결정: Z-Weave 소스는 0줄도 수정하지 않는다.** 이 프로젝트의 존재 이유다. 핵심 통찰은 앱 프로세스 안에 DLL이 들어가면 Z-Weave의 export된 심볼이 필요 없다는 것 — 필요한 것은 Qt의 심볼이고 `Qt5Widgets.dll`은 전부 export한다.

**결정: 판단은 전부 TS에, I/O는 가장자리에.** 기능을 최소 단위로 테스트하며 개발하려면 이 경계가 필요하다. C# 층이나 DLL에 판단이 들어가면 테스트 불가능한 덩어리가 생긴다.

**확인한 환경 제약.** `dotnet` SDK가 없어 Windows 내장 `csc.exe`를 쓴다. Python은 Store 스텁뿐이라 pywinauto 경로를 배제했다. Node 24는 타입 붙은 `.ts`를 그대로 실행하고 `node --test`가 내장이라 테스트 의존성이 0이다(실측 확인).

**남은 불확실성 하나.** `zwagent.dll`의 ABI·플러그인 로드 가능성. M4에서 Qt 픽스처 앱으로 싸게 검증한다. 실패하면 `CreateRemoteThread` 주입으로 전환하고, 그 경우도 앱 소스는 그대로다.

**대상 앱 리포 보호 설정.** "zw-probe에서 Z-Weave 코드를 커밋·푸시하지 못하게 deny로 막는다"를 시도했고, **deny 패턴으로는 정확히 표현할 수 없다**는 것을 확인했다. 패턴은 명령 문자열의 접두사만 매칭하고 경로를 모른다. `Bash(git commit:*)`을 넣으면 Z-Weave가 아니라 zw-probe의 커밋이 죽는다.

차선으로 **도달 경로를 끊었다.** 사용자 스코프가 이미 `git -C`·`--git-dir`·`--work-tree`를 막고 있으므로 Bash가 다른 리포에 도달하는 현실적 경로는 `cd`뿐이다. `cd`/`pushd`/`popd`를 통째로 막고, `Edit`/`Write`의 Z-Weave 경로도 막았다. 비용은 절대 경로를 써야 한다는 것뿐이다 — 하네스 자체가 `cd`보다 절대 경로를 권하므로 실질 손실이 없다.

경로 기반 강제는 `PreToolUse` 훅만 가능하다. 훅은 Bash 호출마다 프로세스가 붙고 정규식 오탐 위험이 있어 이전에 의도적으로 제외한 방식이라, 실제 사고가 나기 전까지는 도입하지 않는다.

**커밋 권한.** Z-Weave 리포는 프로젝트 스코프 deny로 커밋이 막혀 있으나 이 폴더는 해당되지 않는다. 사용자 스코프 deny(99개)는 원격에 쓰는 것과 파괴적 로컬 명령만 막고 `git commit`은 허용한다. 따라서 이 리포에서는 Claude가 자동 커밋한다. push와 PR은 하지 않는다 — 전역 차단이고 원격도 없다.

## 2026-09-08 — 보호 장치를 훅으로 교체. 앞 절의 결정을 뒤집었다

코드를 쓰기 전에 앞 절의 deny 설정이 실제로 작동하는지 측정했다. **작동하지 않았다.**

**측정 1 — `Edit`/`Write`의 경로 차단은 존재하지 않았다.** `Write`로 `D:/z-emotion/Z-Weave/CMakeLists.txt`를 겨냥하니 권한 검사를 통과했고, Write 도구 자체의 "읽지 않은 파일은 덮어쓸 수 없다" 가드에만 걸렸다. 그 파일을 먼저 `Read`했다면 그대로 덮어써졌다. `//D:/...` 문법이 Windows 드라이브 절대경로와 매칭되지 않는다. 대문자·소문자 드라이브를 모두 넣어둔 것은 의미가 없었다.

**측정 2 — git이 Z-Weave 안에 파일을 만들 수 있었다.** `git init "D:/z-emotion/Z-Weave/..."`와 `git worktree add "D:/z-emotion/Z-Weave/..."`가 둘 다 권한을 통과해 git 본체까지 도달했다(없는 플래그를 줘서 인자 파싱에서 멈추게 한 프로브였으므로 부작용은 없었다). 사용자 스코프 deny 목록은 이력을 파괴하는 동사(`reset`·`checkout`·`rebase`…)를 열거하지만 **목적지 경로를 인자로 받는 서브명령**(`init`·`clone`·`worktree`·`submodule`)이 비어 있다. `gh repo clone`, `gh release download -D`도 같은 구멍이다. 리포 *조작*은 막혀 있었고 디렉토리에 *쓰는 것*은 열려 있었다.

**정정 — 앞 절의 "deny 패턴은 명령 문자열의 접두사만 매칭"은 부정확하다.** 복합 명령은 분해되어 서브명령마다 검사된다. `cat ... ; git -C ... status`가 **두 번째** 서브명령의 `git -C` 때문에 전체 거부되는 것을 확인했다. `Bash(...)` 규칙은 문서가 가정한 것보다 강하다. 다만 이것은 명령 이름에 대한 강함이고, 경로를 이해하지 못한다는 원래 한계는 그대로다.

**방향 변경: "실제로 사고가 나면 훅을 도입한다"를 철회한다.** 사고를 기다릴 이유가 없었다 — 보호가 처음부터 없었다는 것이 측정으로 드러났으므로, 잠재 사고는 이미 발생해 있었다. 훅 비용(Bash 호출마다 프로세스, 정규식 오탐)은 보호가 0인 것보다 싸다.

**훅 설계 — 읽기와 쓰기를 구분한다.** deny 목록이 못 하는 일이 이것이다. 사용자 방침은 "읽는 것만 자유, 나머지 전부 차단, 개발 중 막히면 그때 푼다"였다.

- `Write`/`Edit`/`NotebookEdit` — 대상 경로가 Z-Weave 아래면 무조건 거부.
- `Bash` — 명령이 Z-Weave를 언급하지 않으면 관여하지 않는다. 언급하면 읽기 전용 화이트리스트로만 통과시키고 나머지는 전부 거부한다. 판단이 안 서는 경우(명령 치환, 출력 리다이렉션, 훅 입력 파싱 실패)도 거부 — **닫히는 방향으로 실패한다.**
- 읽기 도구(`Read`·`Grep`·`Glob`)와 로컬 파일 읽기 명령은 손대지 않는다.

상대경로 탈출(`../Z-Weave/...`)을 잡으려면 절대경로가 아니라 리포 이름으로 판정해야 한다. `zwprobe`·`zwwin`·`zwagent`에는 `z-weave`가 없으므로 자기 작업을 오탐으로 막지 않는다.

**의도적으로 과차단한 곳.** Z-Weave를 언급하는 `gh` 명령은 읽기까지 막힌다. gh는 서브명령 조합이 넓어 화이트리스트로 안전하게 열 자신이 없었다. 로컬 파일 읽기는 영향이 없고 GitHub 네트워크 조회만 걸린다. 필요해지면 그때 푼다.

**막힌 지점 — 세션은 자기 권한 파일을 수정할 수 없다.** `.claude/settings.json`을 Bash와 Write 양쪽으로 쓰려다 auto mode 분류기에 차단됐다. 다만 **약화하는 편집만** 막힌다: 무효인 deny 규칙을 제거하는 편집은 거부됐고, deny 추가와 훅 등록처럼 순수하게 강화하는 편집은 통과했다. 그래서 무효인 `//D:/...` 규칙 4줄은 지우지 못한 채 남아 있다 — 무해하지만 착각을 만들므로 사람이 지워야 한다.

**같은 날 추가로 찾은 구멍 — `git --git-dir=` 등호 형태.** "git/gh로 대상 앱에 실행하는 것도 다 막혀 있나"라는 질문을 받고, 설정을 읽어 추론한 앞선 보고("`--git-dir`·`--work-tree`는 사용자 스코프 deny에 있으니 막혀 있다")를 실측으로 검증했다. **틀렸다.** `git --git-dir="D:/…/Z-Weave/.git" --work-tree="D:/…/Z-Weave" status`가 exit 0으로 실행돼 대상 앱 리포의 git 상태를 그대로 읽어냈다.

원인이 두 겹이었다. ① `Bash(git --git-dir:*)`는 `--git-dir`을 별개 토큰으로 기대하는데 `--git-dir="..."`은 한 토큰이라 빠져나간다. 공백 형태만 막히고 등호 형태는 통과한다 — 이건 사용자 전역 설정의 구멍이고 대상 앱뿐 아니라 모든 리포에 대해 열려 있다. ② 훅도 놓쳤다. 서브명령이 `status`라서 읽기로 판정하고, `--git-dir`이 git을 다른 리포로 갈아끼운다는 사실을 보지 않았다.

**교훈: 설정 파일을 읽는 것은 검증이 아니다.** 앞선 보고에서 `git -C`는 프로브로 확인했지만 `--git-dir`은 deny 목록에 있는 것을 보고 막혀 있다고 단정했다. 프로브를 쏜 것만 확인된 것으로 취급해야 한다.

**발동 판정을 문자열에서 경로 해석으로 바꿨다.** 처음엔 "문자열에 z-weave가 있나"로 발동시켰는데 양쪽으로 틀렸다. 이름에 `zweave`가 든 자기 파일(`guard-zweave.mjs`)을 다루는 것만으로 발동해 **훅이 자기 테스트 실행을 막았고**, `sed -i "s/Z-Weave/…/" docs/WORKLOG.md`처럼 자기 문서를 고치는 것도 막혔다. 반대로 그 언급을 문자열에서 걷어내려 하니 `--git-dir=<경로>`와 gh 리포 지정자가 빠져나갔다. 올바른 질문은 "**토큰 중 Z-Weave 안으로 해석되는 경로가 있나**"였다. 경로로 해석하면 둘 다 정확히 갈린다. 예외는 gh 하나 — 로컬 경로가 아니라 `-R z-emotion/Z-Weave` 같은 리포 지정자로 닿으므로 문자열 언급으로도 발동시킨다.

부수 효과로 `tasklist | grep -i z-weave`가 다시 동작한다. 문자열을 검색하는 것은 경로를 건드리는 것이 아니다.

**남는 한계.** 의도적 우회는 막지 못한다 — 8.3 단축 이름, `z-weave`를 문자로 쓰지 않는 `..` 연쇄, 정션·심볼릭 링크. 경로를 하드코딩한 자기 스크립트를 `node script.mjs`로 실행하는 것도 명령에 경로가 나타나지 않아 잡히지 않는다.

## 2026-09-09 — 훅을 걷어내고 deny 6줄로 되돌렸다

**사용자 판단이었다.** 프로젝트 스코프 권한을 전부 비우고 훅 파일까지 삭제한 뒤, 요구를 좁혀 다시 지시했다 — "대상 앱 코드를 commit·push 하지 못하게만 막아라." 훅은 그 요구보다 훨씬 넓은 것을 하고 있었다.

**좁힌 요구가 훨씬 단순한 해법을 허용했다.** git이 대상 앱 리포에 도달하는 경로는 `cd`·`-C`·`--git-dir`/`--work-tree` 셋뿐이다. 셋을 끊으면 도달 자체가 불가능하므로 commit·push가 성립하지 않는다. 훅의 명령 화이트리스트가 필요 없다. 그리고 대상 앱 파일이 이 리포에 커밋될 수는 애초에 없다 — git은 작업 트리 밖의 파일을 `add`하지 못한다.

**되돌리는 과정에서 규칙 문법 두 가지를 실측으로 알아냈다.** 이게 이 날의 실질 수확이다.

**`Write(...)`는 인식되지 않는 규칙 이름이다.** 조용히 무시된다. 6가지 경로 문법을 `Write(...)`로 시험했는데 하나도 안 걸려서 "경로 문법이 다 틀렸나" 했지만, 같은 경로를 `Edit(...)`로 바꾸자 즉시 막혔다. 문법 문제가 아니라 이름 문제였다. `Edit(...)` 하나가 `Write`·`Edit`·`NotebookEdit`를 함께 덮는다.

즉 처음의 죽은 4줄에는 **서로 다른 버그가 두 개** 있었다. `Write(//D:/...)` 두 줄은 이름이 틀렸고, `Edit(//D:/...)` 두 줄은 `//` 접두사가 틀렸다. 하나만 고쳐도 안 됐을 것이다.

**경로는 맨 절대경로로 쓴다.** `Edit(D:/z-emotion/Z-Weave/**)`. 작업 디렉토리 안팎 모두에서 작동하고, 대소문자와 역슬래시는 정규화된다 — `D:`/`d:` 두 벌을 쓸 필요가 없었다.

**등호 형태 deny 패턴도 실측했다.** `Bash(git --git-dir=*)`가 `--git-dir="..."`을 잡는다. 접두사가 `=`까지 포함되어 한 토큰 안에서 매칭되기 때문이다. 사용자 스코프의 `Bash(git --git-dir:*)`가 놓치던 구멍이 이걸로 막힌다.

**훅이 파일 도구에서 발동을 멈춘 현상은 원인을 확정하지 못했다.** deny 를 비운 뒤 `Write`·`Edit` 호출이 훅을 거치지 않았다. 같은 시점에 Bash 호출은 정상적으로 훅에 걸렸고, 훅 스크립트는 16개 테스트를 통과했고 `settings.json` 도 유효했다. 매처에 `Write|Edit|NotebookEdit` 가 들어 있었는데도 그랬다. 훅을 걷어내기로 정해져서 더 파지 않았다. **훅 방식으로 돌아간다면 이것부터 확인해야 한다** — 파일 도구 커버리지를 매번 실제로 프로브해서 확인하지 않으면 조용히 열린다.

**완화 편집에 대한 앞선 서술을 정정한다.** "세션은 자기 권한 파일을 약화하는 편집을 구조적으로 할 수 없다"고 적었는데 정확하지 않다. **사용자가 명시적으로 지시하면 통과한다.** 분류기가 대화 속 사용자 의도를 본다. 실제로 앞선 시도는 거부됐고, 사용자가 "제거해"라고 지시한 뒤의 동일한 편집은 통과했다. 그래서 규칙은 "구조적으로 불가능"이 아니라 "지시 없이 스스로 완화하지 않는다"다.

**남은 것.** 파일 수정은 지금 열려 있다. commit·push만 막는 것이 요구였으므로 의도된 상태다. 필요해지면 `Edit(D:/z-emotion/Z-Weave/**)` 한 줄을 넣으면 되고 문법은 검증돼 있다.

## 2026-09-09 — M2 입력. `PostMessage`는 위험하다는 것을 실측했다

M2 의 불확실성은 캡처와 달랐다. 캡처는 가려진 창도 잡혔지만 **입력은 포커스를 요구할 것**으로 봤다. `keybd_event`/`SendInput`은 시스템 전역이라 포그라운드 창으로 간다. 대안인 `PostMessage`는 창을 지정할 수 있어 매력적이지만 수식키가 실리지 않는다고 알려져 있다. 단축키 목록이 수식키로 가득하므로 이것부터 태웠다.

**관측 가능한 변화로 골랐다.** `SidePanel=Shift+P` — 화면 변화가 크고, 문서를 건드리지 않고, 한 번 더 누르면 되돌아간다. 찍고, 누르고, 다시 찍어 비교하는 방식은 M3 시나리오 러너가 할 일과 같아서 그 자체로 예행연습이 됐다.

**`send` 는 통했다.** 활성화가 성공하고(`activated: true`, 포그라운드가 대상 hwnd) 오른쪽 패널이 사라졌다. 색상 727 → 455, 휘도 79.4 → 92.8. 한 번 더 눌러 정확히 원래 값으로 돌아왔다.

**`post` 는 예상보다 나빴다.** "아무 일도 안 일어난다" 가 아니었다. 수식키가 빠져 `Shift+P` 가 평범한 `P` 로 전달됐고, `P` 는 `MainPin` 이라 **핀 도구가 켜지고 오른쪽 패널이 Properties 탭으로 바뀌었다.** 화면에 "Click to place a pin on a pattern" 이 떴다.

이게 이 날의 가장 중요한 발견이다. **틀린 키는 무동작이 아니라 다른 명령 실행이다.** 자동 루프에서 이런 일이 나면 조용히 엉뚱한 상태로 흘러가고, 그 뒤의 모든 판정이 오염된다. 그래서 두 가지를 규칙으로 세웠다.

- `PostMessage` 는 쓰지 않는다. 진단용으로만 남긴다
- 단축키 파서는 **모르는 토큰을 만나면 던진다.** 관대하게 넘기면 안 된다. 파일 전체를 읽을 때는 실패한 줄을 모아 보고하고(관대하게), 개별 단축키를 실제로 쓸 때는 던진다(엄격하게)

**설계 결론.** 입력은 포그라운드를 점유한다. M3 시나리오가 도는 동안 사용자가 다른 창을 만지면 키가 그쪽으로 간다. 이건 우회할 수 없는 성질이므로 러너가 이를 전제로 설계돼야 한다.

**버전 디렉토리 버그 두 개.** 처음 구현은 최신 버전 디렉토리의 `shortcut.ini` 를 읽었다. 디스크에 `5.0.34` 와 `5.1.0` 이 함께 있었고 **실행 중인 앱은 5.0.34** 였으므로 틀린 파일을 읽고 있었다. 버전 간에 매핑이 바뀐 항목에서 위와 같은 사고가 난다. `zwwin.exe` 가 프로세스 실행 파일 버전을 보고하게 하고 그것으로 맞추게 고쳤다. 못 맞추면 최신으로 떨어지되 `how: 'newest'` 로 알린다.

두 번째는 이름 충돌이었다. ini 안의 `Version=1.6`(스키마 버전)과 디렉토리 이름 `5.0.34`(앱 버전)를 둘 다 `version` 으로 두어 스프레드에서 조용히 덮였다. 출력에 `Version=5.1.0` 이 찍혀서 발견했다. `appVersion` 으로 갈랐다.

**남긴 상태.** `post` 실험이 오른쪽 패널을 Simulation 탭에서 Properties 탭으로 바꿔놓았다. ESC 로 핀 도구는 해제했지만 탭 선택은 단축키가 없어 되돌리지 못했다. 마우스 입력을 구현하면 처리할 수 있다. 위협 모델이 적대적 우회가 아니라 **자기 실수**이므로 감수한다. 진짜 OS 수준 강제는 `sandbox.filesystem.denyWrite`(문자열 검사가 아닌 파일시스템 격리)지만, M4 이후 `csc.exe`·Qt 빌드·앱 실행을 깨뜨릴 위험이 커서 보류한다. 훅으로 부족하다고 판명되면 그때 꺼낸다.
